# Research: Extraction Profiles Command

**Feature**: 007-extraction-profiles
**Date**: 2026-02-19

## Research Topics

### 1. Step 0.5 Loading Pattern

**Decision**: Replicate the existing Step 0.5 pattern for loading extraction-profile.md, adding it as Step 0.6 immediately after the project context loading.

**Rationale**: The Step 0.5 pattern is standardized across all Reforge commands (confirmed identical in extract.md lines 70-77 and analyze.md lines 68-75). Adding a Step 0.6 maintains consistency and keeps profile loading separate from project context loading.

**Alternatives considered**:
- Merging into Step 0.5 (rejected: conflates two different files with different purposes)
- Loading at a later step (rejected: language rules need to be available from the start of extraction)

### 2. Language-Specific Rules Section Boundaries

**Decision**: Remove extract.md lines 979-1001 (the `## Language-Specific Extraction Rules` section) plus the trailing `---` separator on line 1002.

**Rationale**: The section contains 23 lines covering VB.NET (6 rules), C# (4 rules), and General (3 rules). Per the clarification session, these rules are removed entirely — they will be generated dynamically by the profile command instead.

**Alternatives considered**:
- Keeping as conditional fallback (rejected per clarification: user wants clean removal)
- Moving to a separate static file (rejected: defeats the purpose of dynamic, per-project profiles)

### 4. Profile File Structure Design

**Decision**: Use a structured markdown format with top-level sections for each concern area, following the same structured markdown pattern used by `project-context.md`.

**Rationale**: The profile is instructional text for the AI agent (not structured extraction output), so markdown is appropriate per Constitution Principle III. The structure mirrors what the agent needs at extraction time.

**Designed structure**:
```markdown
# Extraction Profile

Generated by `/reforge.profile` on YYYY-MM-DD
Languages: [list]
Architecture: [list]

## Language-Specific Extraction Rules

### [Language Name]
- **[Rule category]**: [Extraction guidance]
(5+ rules per known language)

## Architecture-Specific Extraction Guidance

### [Pattern Name]
- [Guidance about where to find business rules, data access, etc.]

## Framework-Specific Patterns

### [Framework Name]
- [Framework-specific extraction patterns]

## Custom Extraction Notes
- [User-provided project-specific guidance]
```

**Alternatives considered**:
- XML format (rejected: profile is guidance text, not structured data; Principle III allows markdown)
- JSON format (rejected: less readable for the AI agent as inline guidance)
- Embedding in project-context.md (rejected: different lifecycle and purpose; spec explicitly separates them)

### 5. LLM-Driven Language Knowledge Strategy

**Decision**: The profile.md command template contains instructional prompts that guide the agent to generate language-specific rules from its training knowledge for ANY declared language. The template includes structured prompts for 5 universal categories (type system, operators, naming, pitfalls, frameworks) and the LLM generates the actual rules at runtime. There is no finite "supported languages" list — the LLM has training knowledge of virtually all established programming languages including legacy and enterprise languages (COBOL, Fortran, Assembly, FoxPro, RPG, MUMPS, Ada, ABAP, etc.).

**Rationale**: Per Constitution Principle I (LLM-First), the LLM's semantic understanding of programming languages IS the source of knowledge. Hardcoding a catalog of rules in the template would be both large and incomplete. Instead, the template instructs the agent on WHAT categories of rules to generate, and the agent fills in the specifics from its knowledge of the declared language.

**Example prompt pattern**:
```
For each declared language, generate extraction rules covering:
1. Type system quirks that affect extraction accuracy
2. Operator differences that could be misrecorded
3. Naming conventions and case sensitivity rules
4. Common pitfalls when extracting identifiers or values
5. Framework-specific patterns relevant to business rule extraction
```

**Alternatives considered**:
- Hardcoding a full catalog per language (rejected: would make profile.md 500+ lines; incomplete by nature; contradicts LLM-First principle)
- Using Context7 to fetch language docs (rejected: requires MCP server, violates Principle V agent-agnostic)

### 6. Update Mode Behavior

**Decision**: The `--update` flag causes the command to load the existing profile, present current languages/architecture to the user, allow additions and removals, then regenerate only the changed sections while preserving unchanged content.

**Rationale**: Users discover new technologies during iterative analysis. Regenerating the entire profile would lose custom notes and any manual edits. Preserving unchanged sections respects the user's prior work.

**Alternatives considered**:
- Full regeneration every time (rejected: loses custom notes and manual edits)
- Append-only mode (rejected: no way to remove obsolete languages)
