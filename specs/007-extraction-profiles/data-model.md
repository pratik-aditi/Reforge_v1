# Data Model: Extraction Profiles Command

**Feature**: 007-extraction-profiles
**Date**: 2026-02-19

## Overview

This feature creates a new command template and modifies an existing one. The "data model" is the structure of the generated extraction profile file and the modifications to the existing extract command template.

## File: `.reforge/commands/profile.md` (NEW)

**Type**: Prompt template command
**Purpose**: Interactive command that gathers technology stack info and generates an extraction profile
**Pattern**: Follows `/reforge.init` interactive Q&A pattern
**Size estimate**: ~200-300 lines

### Section Structure

1. **Command Syntax** — Header with `/reforge.profile [--update]` syntax and arguments table
2. **Overview** — Purpose description
3. **Workflow Steps**:
   - Step 0: Check prerequisites (`.reforge/memory/` exists)
   - Step 0.5: Load project context (standard pattern)
   - Step 1: Check existing profile (handle `--update` vs fresh)
   - Step 2: Gather languages (interactive + auto-discovery)
   - Step 3: Gather architecture patterns (interactive)
   - Step 4: Gather custom extraction notes (free-form)
   - Step 5: Generate profile (write to memory)
   - Step 6: Confirm and suggest next steps

### Auto-Discovery Sub-workflow (Step 2)

When the user does not declare languages or requests auto-discovery:

1. Agent runs Glob for common file extensions in the project root (respecting config.json exclusions)
2. Extension-to-language mapping (starting from analyze.md convention, expanded for legacy/enterprise coverage):
   - **Modern languages**: `.cs` → C#, `.java` → Java, `.py` → Python, `.go` → Go, `.rs` → Rust, `.swift` → Swift, `.kt`/`.kts` → Kotlin, `.scala` → Scala, `.dart` → Dart, `.jl` → Julia
   - **Web/scripting**: `.js`/`.mjs`/`.jsx` → JavaScript, `.ts`/`.tsx` → TypeScript, `.rb` → Ruby, `.php` → PHP, `.lua` → Lua, `.r` → R, `.pl`/`.pm` → Perl
   - **Legacy/enterprise**: `.vb` → VB.NET, `.cob`/`.cbl` → COBOL, `.f`/`.f90`/`.f95`/`.f03` → Fortran, `.prg`/`.scx`/`.vcx`/`.frx` → FoxPro, `.asm`/`.s` → Assembly, `.rpgle`/`.rpg` → RPG, `.abap` → ABAP, `.bas` → BASIC, `.rex`/`.rexx` → REXX, `.m` → MUMPS (or Objective-C — ask user to disambiguate)
   - **Systems**: `.cpp`/`.cc`/`.c`/`.h`/`.hpp` → C/C++, `.adb`/`.ads` → Ada, `.pas`/`.dpr` → Delphi/Pascal, `.d` → D
   - **Functional**: `.hs` → Haskell, `.erl` → Erlang, `.ex`/`.exs` → Elixir, `.clj`/`.cljs` → Clojure, `.ml`/`.mli` → OCaml, `.fs`/`.fsx` → F#
   - **Data/query**: `.sql` → SQL, `.aspx`/`.ascx` → ASP.NET, `.groovy` → Groovy
   - **Catch-all**: For any other file extensions found that the agent recognizes as source code for a programming language, include those languages as well. The list above is a convenience mapping for Glob scanning — it is NOT a boundary on supported languages. The LLM has training knowledge of virtually all established programming languages.
3. For ambiguous extensions (e.g., `.h` → C or C++, `.m` → MUMPS or Objective-C), present options to user for disambiguation
4. Present discovered languages with file counts to user for confirmation
5. User confirms, adds, or removes from the discovered list — users may also declare languages manually even if no matching files were found (e.g., declaring COBOL when source files use non-standard extensions)
6. Proceed to profile generation with confirmed languages

### LLM-Driven Language Knowledge Prompts

For each declared language (ANY language — there is no restriction), the template instructs the agent to generate rules from its training knowledge covering 5 categories:

| Category | Description | Example (VB.NET) |
|----------|-------------|-------------------|
| Type system quirks | Language-specific type behaviors that affect extraction accuracy | Array upper bounds, Nothing vs null, Option Strict |
| Operator differences | Operators that could be misrecorded or paraphrased | OrElse vs Or, AndAlso vs And |
| Naming conventions | Case sensitivity and identifier patterns | PascalCase methods, Handles keyword |
| Common pitfalls | Extraction errors specific to this language | String-typed enums via custom base class |
| Framework patterns | Framework-specific extraction guidance | WCF service contracts, Entity Framework DbContext |

## File: `.reforge/memory/extraction-profile.md` (GENERATED AT RUNTIME)

**Type**: Structured markdown output
**Purpose**: Language-specific, architecture-specific, and custom extraction guidance read by the extract command
**Created by**: `/reforge.profile` command
**Read by**: `/reforge.extract` command (via Step 0.6)

### Section Structure

```markdown
# Extraction Profile

Generated by `/reforge.profile` on YYYY-MM-DD
Languages: VB.NET, C#, SQL
Architecture: Layered with repository pattern

## Language-Specific Extraction Rules

### VB.NET
- **Array declarations**: `Dim arr(6)` creates 7 elements (0-6), not 6
- **Boolean operators**: `OrElse` is short-circuit (different from `Or`)
- **Option Strict**: When On, implicit conversions disallowed
- **Custom enum patterns**: May use `Enumeration(Of TValue, TEnum)` base class
- **String comparison**: `=` performs value comparison by default
- **Nothing**: Equivalent to null but also default(T) for value types

### C#
- **Line counting**: Files may lack trailing newline; wc -l undercounts by 1
- **nameof()**: Produces compile-time string; extract the actual string value
- **Null-conditional**: `?.` and `??` — describe actual null-handling behavior
- **Pattern matching**: Extract full switch expression patterns, not simplified versions

### SQL
- **Dialect awareness**: Note specific SQL dialect (T-SQL, PL/SQL, MySQL)
- **Stored procedure parameters**: Extract exact parameter names and types
- **Dynamic SQL**: Flag string-built queries; extract the template pattern
- **Transaction boundaries**: Note explicit BEGIN/COMMIT/ROLLBACK scoping
- **Temp tables vs table variables**: Distinguish scope and lifetime differences

## Architecture-Specific Extraction Guidance

### Layered Architecture
- **Business rules location**: Service/Manager/Handler classes in the business/service layer
- **Data access location**: Repository/DataAccess/Context classes in the data layer
- **Cross-layer calls**: Trace dependency injection to map layer relationships
- **Workflow location**: Orchestrator/Coordinator/Pipeline classes

## Framework-Specific Patterns
(generated based on declared frameworks)

## Custom Extraction Notes
- All business rules are in classes ending with 'Manager'
- Legacy COM interop wrappers in /Interop/ directory should be traced to original sources
```
