Architecture Review · Internal

extract.md under a 5–6 Sonnet sub-agent topology

A correctness-first extraction pipeline, read literally, produces a redundant-I/O problem the moment it is parallelized. This review traces the mechanism, isolates the root cause, and proposes a broker-mediated architecture that preserves the correctness guarantee while removing the redundancy tax.

Subject: .reforge/commands/extract.md Scope: 10 extraction types, 5–6 sub-agent dispatch model Classification: Architecture review · not a production incident report

01 System context & the correctness paradox

extract.md's single strongest guarantee is also its single largest cost center. Understanding why requires taking the rule at its word before deciding what to change.

Step 1 of every extraction type in extract.md states the constraint plainly:

"Do NOT extract from memory of previous sessions or from analysis.xml metadata alone... only reference files read in this session." extract.md, Step 1 — CRITICAL, applies uniformly to all 10 extraction types

This exists to prevent a specific, well-documented LLM failure mode: an agent that has "seen" a file once treats its own prior summary, or the coarse metadata in analysis.xml, as if it were the file itself, and starts reconstructing identifiers, method signatures, and enum members from plausible-sounding memory rather than from the literal bytes on disk. The rest of the command reinforces this relentlessly — verbatim-copy mandates for identifiers and operators, a requirement to re-verify every written identifier against a fresh Read, and a confidence rubric that explicitly downgrades anything not re-confirmed against source in the current session.

The conflation

The rule protects one property — byte provenance: is this content genuinely, verifiably the source code, not a paraphrase? — but it enforces that property through one specific mechanism: session-scoped I/O, a fresh Read tool call inside the current invocation. Those are not the same thing. Provenance is about what the content is. Session-scoped I/O is about how the content arrived. extract.md was authored as if the second were the only possible implementation of the first — which was true for a single-agent, single-invocation design, and stops being true the moment a shared, content-verified cache enters the picture.

That distinction is the entire thesis of this review. If provenance can be guaranteed by a mechanism other than "the requesting agent personally issued the disk read," the rule's intent is preserved and its cost structure changes completely. Section 3 formalizes this as a root-cause split between trust boundary and transport mechanism; Section 4's first recommendation is the direct architectural consequence.

02 Redundancy mechanics: sequential vs. concurrent

Walking one real file through the pipeline makes the abstract cost concrete.

Take OrderController.java, an illustrative ~3,500 LOC controller class typical of the cross-cutting files found in any mature service layer. It contains pricing conditionals (relevant to business-rules), is an entry point for order submission (relevant to workflows), makes several outbound calls into repository and pricing services (relevant to call-sites), imports and injects five or six collaborators (relevant to dependencies), and sits at a layer boundary worth documenting (relevant to architecture). Five extraction domains, one file.

Sequential CLI execution

Run as the README's typical workflow prescribes — one /reforge.extract <type> invocation after another — each of those five passes is its own session. Each one independently satisfies Step 1 by opening OrderController.java, reading it in full, running its own detection patterns, and discarding the raw content when the invocation ends. The file is read from disk five separate times, at five separate points on the clock, with zero memory of the previous four reads.

Naive concurrent sub-agent execution

Parallelizing the same five domains across five or six live Sonnet sub-agents does not remove the redundancy — it compresses it into a single instant. All five domain agents that touch this file request it at approximately t₀, independently, with no coordination layer between them. Functionally this looks identical to the sequential case from the rule's perspective (five sessions, five satisfied Step-1 mandates), but it introduces two failure modes sequential execution does not have:

Anti-pattern flag

Naively parallelizing extraction types without a mediation layer converts a linear redundancy cost into a bursty one. The total wasted tokens do not increase, but the shape of the waste changes from "spread thin over 30 minutes" to "concentrated in a few seconds," which is precisely the pattern that trips per-minute rate ceilings and turns a theoretical speedup into unpredictable throttling in production.

03 Root cause analysis

The redundancy is not a bug in extract.md. It is the correct, intended behavior of a rule that was never asked to distinguish two things it happens to conflate.

LayerQuestion it answersWhat extract.md actually enforcesFailure mode if the layers are conflated
Semantic trust boundary Is this content genuinely, verifiably the source code — not a paraphrase, not a hallucinated reconstruction? Verbatim-copy mandates; mandatory re-verification of every identifier against a fresh Read; confidence downgraded to medium/low whenever verification is incomplete A fabricated identifier gets silently promoted to confidence="high" because nothing checked it against real bytes
Transport / retrieval mechanism By what physical or logical path did these bytes arrive in the agent's context? "only reference files read in this session" — interpreted as a literal, agent-local disk read Content that is provably identical and provably verbatim is re-fetched from disk anyway, purely because a different agent's syscall retrieved it

RCA finding. At the time extract.md was authored for a single-agent, single-invocation execution model, session-scoped I/O and byte provenance were functionally identical — the only way to guarantee you were looking at real source was to personally read it, because there was no other trustworthy channel. The rule encodes the mechanism (I/O timing) rather than the property it protects (provenance), because under the original execution model there was no daylight between the two.

A multi-agent topology introduces daylight. A content-hashed cache can deliver the exact same verbatim bytes, byte-for-byte, to a second, third, and fourth agent, with cryptographic proof (a SHA-256 match) that nothing was altered, paraphrased, or summarized in transit. That satisfies the trust boundary completely. It just doesn't satisfy the transport mechanism as originally — and unnecessarily — specified.

Architectural decision

Treat "read in this session" as shorthand for "verified, unaltered, and traceable to a specific read event" — not as a literal mandate that each agent must independently perform its own disk syscall. Any mechanism that can prove the former (hash-verified, provenance-tagged content) satisfies the rule's intent regardless of which agent originally triggered the physical read.

04 Strategic architecture recommendations

Four changes, ordered so that each one remains valid independent of whether the others are adopted.

Recommendation 1 — Verbatim content-hashed read cache (Tier 1)

Key the cache on the tuple (canonical_path, sha256_hash), not on path alone. Path-only keying is stale-prone — a file edited mid-run would silently serve outdated content. Hash-keying makes the cache self-invalidating: if the file changes, its hash changes, the tuple no longer matches, and the next request is automatically treated as a cold read. This is what makes "zero-interpretation byte streaming" defensible against the correctness mandate — the cache never summarizes, truncates, or transforms; it stores and replays the exact byte sequence the first reader saw, with a cryptographic receipt attached.

Cache entry contract interface CacheEntry { canonicalPath: string; // repo-root-relative, normalized sha256: string; // content hash at time of first read content: string; // verbatim source text, unmodified firstReadByAgent: string; // provenance tag, e.g. "business-rules" firstReadAtMs: number; servedToAgents: string[]; // audit trail of every cache hit consumer }

Because the entry retains firstReadByAgent and a growing servedToAgents audit trail, every downstream extraction can still cite exactly which physical read event its content traces back to — satisfying any future audit of "was this actually read from disk, by whom, and when" without requiring that every consumer be that same agent.

Recommendation 2 — Upstream relevance manifests

The current design has every extraction type scan every file in analysis.xml's inventory to discover relevance for itself, per invocation. A lightweight AST/parser pre-pass during /reforge.analyze — not a semantic extraction, just structural signal detection (presence of conditionals, SQL strings, DOM markup, import statements, annotations) — can produce a per-file relevance manifest once, shared by every downstream type and every sub-agent.

Relevance manifest — per-file entry { "file": "src/controller/OrderController.java", "sha256": "9f2a1c...c471", "size_tokens": 4500, "relevance": { "business-rules": { "confidence": "high", "signal_count": 14 }, "workflows": { "confidence": "high", "signal_count": 9 }, "call-sites": { "confidence": "high", "signal_count": 22 }, "dependencies": { "confidence": "medium", "signal_count": 6 }, "architecture": { "confidence": "medium", "signal_count": 3 }, "database": { "confidence": "low", "signal_count": 1 }, "ui": { "confidence": "none", "signal_count": 0 } } }

A sub-agent consults this manifest before requesting a file. Types with "none" or negligible signal counts (here, ui) skip the file entirely — a false-positive read prevented, not merely a redundant one deduplicated. This is complementary to Recommendation 1, not a substitute: the manifest reduces how many agents ever ask for a file; the cache handles what happens when more than one still does.

Recommendation 3 — Semantic domain consolidation

workflows and call-sites both trace method-call chains through the same execution paths; dependencies and architecture both perform module/layer-level structural analysis. Dispatching them as a single combined pass per pair — one sub-agent, one file read, two detection procedures run against the same in-context content — removes the redundancy at its source rather than caching around it.

Recommendation 4 — Coordinator-broker pattern

Recommendations 1–3 describe policy. This is the runtime component that enforces it. A deterministic broker daemon sits between every sub-agent and the filesystem: it owns the content-hashed cache, holds a per-path lock so concurrent requests for the same cold file collapse into a single physical read, and serves every subsequent request — from any agent — out of the warm cache.

Diagram 3 — Coordinator-broker topology. Sub-agents never touch the filesystem directly. The broker guarantees at most one physical read per unique file regardless of how many domains, or how many concurrent agents, request it.

Broker API interface interface FileBroker { // Blocks concurrent duplicate requests behind a per-path lock read(request: FileReadRequest): Promise<FileReadResult>; } interface FileReadRequest { canonicalPath: string; requestingAgent: string; // e.g. "workflows-callsites" expectedHash?: string; // optional, from the relevance manifest } interface FileReadResult { canonicalPath: string; sha256: string; content: string; // byte-for-byte verbatim source cacheStatus: "MISS_COLD_READ" | "HIT_WARM_CACHE"; firstReadByAgent: string; servedAtMs: number; }

The lock is the detail that matters most under concurrency: without it, five sub-agents that all miss the cache at t₀ would still fire five simultaneous cold reads before any of them populates the cache. The broker must treat a cold request for a path that is already in flight as a queue-and-wait, not a new read, collapsing the Diagram 2 burst into the single cold read shown in Diagram 3.

Anti-pattern flag

The naive-concurrent row looks fastest on paper. It is also the least reliable: its 5.4-minute estimate assumes no rate-limit backoff and no storage contention, both of which Section 2 identifies as realistic risks precisely because five to six large-context requests for the same file land in the same narrow time window. The broker topology's ~2.3–2.5 minute estimate is slower on paper than the unthrottled naive case, but it is the only one of the four that does not depend on an optimistic assumption holding true in production.

06 Recommended adoption order

Each recommendation is independently valid; this is the order that front-loads the highest ratio of savings to implementation risk.

1
Content-hashed read cache (Rec. 1). Delivers the entire 42.9% disk-read reduction and the bulk of the 37.3% cost reduction on its own. Self-contained, no changes to /reforge.analyze required, and it is the recommendation that most directly resolves the RCA's core conflation.
2
Coordinator-broker pattern (Rec. 4). Required to make Rec. 1 safe under concurrency — without the per-path lock, a parallel sub-agent topology will still fire simultaneous cold reads before the cache populates.
3
Semantic domain consolidation (Rec. 3). Cuts dispatch volume and lock contention on top of the cache. Lower urgency than 1–2 because its savings are additive, not foundational — but it is the only lever that reduces the number of agents in the first place.
4
Upstream relevance manifests (Rec. 2). Highest implementation cost (an AST/parser pre-pass is new surface area for a framework whose constitution otherwise forbids parsers in the core workflow). Adopt last, and treat it as an optional tooling-layer extension per extract.md's own Constitution Principle VI, not a core-path requirement.
