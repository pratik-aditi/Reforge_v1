# Phase 4: Self-Audit

> Independent quality gate — re-verify entries modified in Phase 3 and all low-confidence entries by re-running verification from scratch. The agent MUST NOT trust Phase 3 results; every check is performed independently.

**Recommended Model Tier**: Accurate (independent re-verification requires careful analysis)

## Input / Output

| Direction | Artifact | Path | Version |
|-----------|----------|------|---------|
| Input | Glossary XML | `$GLOSSARY_XML` | v1.2.0 |
| Input | Audit Report | `$GLOSSARY_AUDIT` | From Phase 3 |
| Output | Glossary XML | `$GLOSSARY_XML` | v1.3.0 (final) |
| Output | Audit Report | `$GLOSSARY_AUDIT` | Updated with Phase 4 findings |

## Variables

These variables are passed by the parent orchestrator (`glossary.md`):

- `$PROJECT_NAME` — project identifier
- `$REPO_ROOT` — absolute path to repository root
- `$PROJECT_OUTPUT_DIR` — output directory for this project
- `$GLOSSARY_XML` — path to `acronym-glossary.xml`
- `$GLOSSARY_AUDIT` — path to `glossary-audit-report.xml`
- `$TEAM_SIZE` — number of worker agents (used for optional parallel processing)

---

## Workflow

### Step 1: Load v1.2.0 Glossary

Read `$GLOSSARY_XML`. Verify the root `<acronym-glossary>` element has `version="v1.2.0"`. If the version is not `v1.2.0`, report an error:

> "Phase 4 requires a v1.2.0 glossary (Phase 3 output). Found version {version}."

Parse all `<entry>` elements into an in-memory working set. Record the total entry count as `$TOTAL_ENTRIES`.

### Step 2: Load Phase 3 Audit Report

Read `$GLOSSARY_AUDIT`. Parse the `<findings>` section and extract all `<finding>` elements where `phase="3"`. Build a lookup of Phase 3 findings keyed by `entry-id` for comparison during re-verification.

Also parse the `<summary>` section — the `<phase-3-summary>` element will be preserved and a `<phase-4-summary>` will be appended alongside it.

### Step 3: Build Re-Verification Queue

Build the set of entries requiring independent re-verification. An entry qualifies if ANY of the following conditions are true:

1. **Modified in Phase 3**: The entry has `version-modified="v1.2.0"`
2. **Low confidence**: The entry has `confidence` < 1.0

These conditions may overlap. Deduplicate the queue so each entry appears exactly once.

Record the queue size as `$QUEUE_SIZE`. Report:

> "Phase 4 re-verification queue: {$QUEUE_SIZE} entries ({modified-count} modified in Phase 3, {low-confidence-count} with confidence < 1.0, {overlap-count} in both categories)"

If `$QUEUE_SIZE` is 0, skip to Step 6 (no re-verification needed). Report:

> "All entries have confidence = 1.0 and none were modified in Phase 3. No re-verification needed."

### Step 4: Independent Re-Verification

For each entry in the re-verification queue, perform independent verification from scratch. Do NOT rely on Phase 3 results — re-run every check.

#### 4a: Independent Word-Boundary Grep

Run a word-boundary grep for the entry's term across all source files under `$REPO_ROOT`:

```
Grep pattern: \bTERM\b
```

**LLM-Authored File Exclusion**: Exclude matches from the following files, as they are generated by the LLM and do not constitute valid source evidence:

- `CLAUDE.md`
- `README.md`
- `project-context.md`
- `analysis.xml`
- Any file under `.reforge/`

Record the Phase 4 grep count as `$P4_GREP_COUNT`.

#### 4b: Compare Grep Counts

Look up the Phase 3 finding for this entry (from the Step 2 lookup). Compare:

- `$P3_GREP_COUNT` = Phase 3 finding's `grep-count` attribute
- `$P4_GREP_COUNT` = independently computed count from Step 4a

If `$P4_GREP_COUNT` differs from `$P3_GREP_COUNT`:
- Flag as **potential hallucinated count** in the finding rationale
- Use `$P4_GREP_COUNT` as the authoritative count (Phase 4 takes precedence)

If the entry has no Phase 3 finding (e.g., it was queued only due to low confidence and was not audited in Phase 3), use `$P4_GREP_COUNT` as the sole reference.

#### 4c: Independent Verdict Determination

Determine the Phase 4 verdict independently based on the authoritative grep count and source evidence. Do NOT simply confirm the Phase 3 verdict — re-evaluate from scratch:

| Condition | Verdict | Action | Confidence Update |
|-----------|---------|--------|-------------------|
| `$P4_GREP_COUNT` = 0 AND entry not already `FABRICATED` | `FABRICATED` | `DELETE` | Set to 0.0 |
| `$P4_GREP_COUNT` > 0 AND entry currently `FABRICATED` | `CONFIRMED` or `UNVERIFIABLE` | `KEEP` or `FLAG_FOR_REVIEW` | Re-evaluate based on evidence |
| `$P4_GREP_COUNT` > 0 AND expansion verified in source comments/docs | `CONFIRMED` | `KEEP` | Boost toward 1.0 |
| `$P4_GREP_COUNT` > 0 AND expansion NOT verifiable in source | `UNVERIFIABLE` | `FLAG_FOR_REVIEW` | Cap at 0.5 |

**Expansion verification**: When `$P4_GREP_COUNT` > 0, read the matching source files and check whether the expansion text (or recognizable fragments of it) appears near the term. Look for:
- Doc comments or code comments that spell out the expansion
- String literals containing the full expansion
- Variable/class names that encode the expansion words
- Namespace or package names reflecting the expansion

If the expansion is verified in source, the verdict is `CONFIRMED`. If the term exists but the expansion cannot be independently confirmed, the verdict is `UNVERIFIABLE`.

#### 4d: Record Phase 4 Finding

For each entry in the queue, create an `<finding>` element:

```xml
<finding entry-id="{id}" term="{term}" phase="4"
         verdict="{verdict}" grep-count="{$P4_GREP_COUNT}" action="{action}">
  <evidence-files>
    <file>{matching-file-1}</file>
    <file>{matching-file-2}</file>
  </evidence-files>
  <!-- Include <original-expansion> and <corrected-expansion> only if verdict is CORRECTED -->
  <rationale>{explanation including grep count comparison if counts differed}</rationale>
</finding>
```

The `<rationale>` MUST include:
- The independent grep count
- Whether the grep count matched or differed from Phase 3
- The basis for the verdict (what evidence was or was not found)

### Step 5: Apply Final Corrections

Apply corrections to the glossary based on Phase 4 findings:

#### 5a: Remove FABRICATED Entries

Remove all entries with a Phase 4 verdict of `FABRICATED` from the glossary. These entries had zero word-boundary grep matches and no valid source evidence.

Also remove any entries that were already marked `FABRICATED` in Phase 3 and were NOT upgraded by Phase 4 (i.e., Phase 4 did not find them in the re-verification queue, or re-confirmed the `FABRICATED` status).

Record `$DELETED_COUNT`.

#### 5b: Update Confidence Scores

For entries that remain in the glossary, update confidence scores based on Phase 4 findings:

| Phase 4 Verdict | Confidence Update |
|-----------------|-------------------|
| `CONFIRMED` | Set to 1.0 (independently verified) |
| `CORRECTED` | Set to 0.9 (corrected with evidence) |
| `UNVERIFIABLE` | Cap at 0.5 |
| `FABRICATED` | N/A (entry removed) |

#### 5c: Update Entry Metadata

For each entry modified in Phase 4:
- Set `version-modified="v1.3.0"`
- Update `verification-status` to match the Phase 4 verdict:
  - `CONFIRMED` finding verdict maps to `CONFIRMED` entry status
  - `CORRECTED` finding verdict maps to `CORRECTED` entry status
  - `UNVERIFIABLE` finding verdict maps to `UNVERIFIED` entry status

If a Phase 4 finding adds new evidence (e.g., a source file not previously recorded), add a new `<source>` element to the entry's `<evidence>` container with `phase="4"`.

### Step 6: Update Glossary XML Version

Update the root `<acronym-glossary>` element:
- Set `version="v1.3.0"`
- Update `generated` timestamp to the current ISO-8601 time

Update `<metadata>`:
- Set `<total-count>` to the surviving entry count (after deletions)
- Recalculate `<confidence-distribution>` based on updated confidence scores:
  - `high`: entries with confidence 0.8 - 1.0
  - `medium`: entries with confidence 0.5 - 0.79
  - `low`: entries with confidence 0.0 - 0.49

### Step 7: Write Final Glossary

Write the updated glossary XML to `$GLOSSARY_XML`. This is the final v1.3.0 glossary.

### Step 8: Append Phase 4 Findings to Audit Report

Update the audit report with Phase 4 results:

#### 8a: Update Root Attributes

Update the `<glossary-audit-report>` root element:
- Set `glossary-version="v1.3.0"`
- Update `generated` timestamp
- Update `total-findings` to include Phase 4 findings
- Recalculate `confirmed-count`, `corrected-count`, `fabricated-count`, `unverifiable-count` to reflect the cumulative totals from Phases 3 and 4

#### 8b: Append Phase 4 Findings

Add all Phase 4 `<finding>` elements (from Step 4d) to the `<findings>` container. Phase 3 findings remain unchanged.

#### 8c: Add Phase 4 Summary

Add a `<phase-4-summary>` element to the `<summary>` section alongside the existing `<phase-3-summary>`:

```xml
<summary>
  <phase-3-summary entries-audited="{...}" confirmed="{...}" corrected="{...}"
                   fabricated="{...}" unverifiable="{...}" elapsed-time="{...}"/>
  <phase-4-summary entries-re-verified="{$QUEUE_SIZE}" confirmed="{count}"
                   corrected="{count}" fabricated="{count}"
                   unverifiable="{count}" elapsed-time="{elapsed}"/>
</summary>
```

The `<phase-4-summary>` attributes:
- `entries-re-verified`: Number of entries in the re-verification queue
- `confirmed`: Entries confirmed by Phase 4
- `corrected`: Entries corrected by Phase 4
- `fabricated`: Entries newly identified as fabricated by Phase 4
- `unverifiable`: Entries that could not be verified by Phase 4
- `elapsed-time`: Wall-clock time for Phase 4 execution

### Step 9: Write Updated Audit Report

Write the updated audit report to `$GLOSSARY_AUDIT`.

### Step 10: Report Final Summary

Report the Phase 4 summary to the operator:

> "Phase 4 (Self-Audit) complete."
> "- Entries re-verified: {$QUEUE_SIZE}"
> "- Verdicts: {confirmed} CONFIRMED, {corrected} CORRECTED, {fabricated} FABRICATED, {unverifiable} UNVERIFIABLE"
> "- Grep count discrepancies: {discrepancy-count} (hallucinated counts corrected)"
> "- Entries removed: {$DELETED_COUNT}"
> "- Final glossary: {surviving-count} entries at v1.3.0"
> "- Audit report updated: {$GLOSSARY_AUDIT}"

Signal the orchestrator to:
1. Persist the glossary to memory (`$GLOSSARY_MEMORY`)
2. Save the Phase 4 checkpoint
3. Report the final pipeline summary

## Key Principles

1. **Independent Re-Verification**: The agent MUST re-run every grep and re-read every source file independently. Phase 3 results are inputs for comparison, not trusted facts.

2. **Phase 4 Grep Count is Authoritative**: When Phase 3 and Phase 4 grep counts disagree, the Phase 4 count is the ground truth. This catches hallucinated counts from Phase 3.

3. **Upgrade and Downgrade**: Phase 4 can both upgrade entries (e.g., `FABRICATED` in Phase 3 but found by Phase 4 grep) and downgrade entries (e.g., `CONFIRMED` in Phase 3 but Phase 4 finds zero matches). The independent check is the arbiter.

4. **LLM-Authored File Exclusion**: Matches in LLM-authored files (`CLAUDE.md`, `README.md`, `project-context.md`, `analysis.xml`, any `.reforge/` files) MUST NOT count as valid source evidence. These files may contain the agent's own prior output and would create circular verification.

5. **Evidence Traceability**: Every Phase 4 finding must include a rationale explaining what was checked, what was found, and how the verdict was determined. This provides an audit trail for the quality gate.

---

## Optional: Parallel Processing

When `$TEAM_SIZE` > 1 and the agent supports team orchestration:

1. Partition the re-verification queue across `$TEAM_SIZE` workers
2. Each worker independently runs grep and evaluates verdicts for its assigned entries
3. The lead agent collects findings and applies corrections to the glossary

When `$TEAM_SIZE` = 1 or team orchestration is unavailable: Process entries sequentially as described above. Output is identical regardless of execution path.
